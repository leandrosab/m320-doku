Programmierparadigmen

Ein Paradigma ist die Denkweise, nach der ein Programm aufgebaut wird. In M319 hast du strukturiert/prozedural programmiert, in M320 geht es objektorientiert weiter.

Strukturiert/prozedural vs. objektorientiert

KriteriumStrukturiert / prozedural (C, Pascal)Objektorientiert (C#, Java, C++)
GrundbausteinFunktion / ProzedurKlasse und deren Objekte
Daten und Logikgetrennt: Daten in Variablen/Structs, Logik in Funktionenzusammen in der Klasse gekapselt
AblaufProgramm ruft Funktionen nacheinander aufObjekte senden sich Nachrichten (Methodenaufrufe)
DatenschutzDaten meist global/frei zugänglichZugriff über Sichtbarkeiten gesteuert (private…)
WiederverwendungFunktionen kopieren oder aufrufenVererbung, Polymorphie, Komposition
ModellierungAblauf der VerarbeitungAbbild der realen Welt (Kunde, Rechnung, Auto)
Prüfungsantwort in einem Satz

Beim strukturierten Programmieren sind Daten und Funktionen getrennt und das Programm ist eine Folge von Funktionsaufrufen; beim objektorientierten Programmieren werden Daten und die dazu passenden Methoden in Klassen zusammengefasst, aus denen zur Laufzeit Objekte entstehen.

Weitere Paradigmen (nur zur Einordnung)

  • Prozedural: Pascal, C
  • Objektorientiert: C#, C++, Java
  • Logisch: Prolog
  • Funktional: F#, JavaScript

Die vier Säulen der OOP

Das ist die sicherste Frage der ganzen Prüfung: aufzählen und je mit einem Codebeispiel erklären. Merkwort: KAVP – Kapselung, Abstraktion, Vererbung, Polymorphie.

SäuleEnglischKern in einem Satz
KapselungEncapsulationDaten und Logik werden zu einem neuen Datentyp zusammengefasst; das Objekt gibt nur ausgewählte Informationen preis und verpackt den Rest.
AbstraktionAbstractionDas Objekt versteckt Details und bietet Operationen auf einer höheren Bedeutungsebene an, um Komplexität zu reduzieren.
VererbungInheritanceEin neuer Datentyp übernimmt die Funktionalität eines bestehenden und erweitert oder verändert sie.
PolymorphiePolymorphismVielgestaltigkeit: Typen mit gemeinsamer Schnittstelle definieren eigenes Verhalten und sind dadurch austauschbar.

Kapselung – Beispiel FullName

Vorname und Nachname gehören zusammen, also kommen sie mit ihrer Logik in eine Klasse. Von aussen sieht man nur die Methoden, nicht die Felder.

C# · Kapselung
class FullName
{
    private string _firstName;   // versteckte Daten
    private string _lastName;

    public FullName(string firstName, string lastName)
    {
        _firstName = firstName;
        _lastName = lastName;
    }

    public string FormatDefault()   // sichtbare Schnittstelle
    {
        return $"{_firstName} {_lastName}";
    }

    public string FormatSwiss()
    {
        return $"{_lastName}, {_firstName}";
    }
}

FullName joe = new FullName("Joe", "Doe");
Console.WriteLine(joe.FormatDefault());  // Joe Doe
Console.WriteLine(joe.FormatSwiss());    // Doe, Joe

Bild dazu: ein elektronisches Gerät versteckt die komplizierten Vorgänge und bietet nur eine einfache Bedienoberfläche an.

Abstraktion – Beispiel Counter

Ein Zähler ist fast wie eine Zahl, aber mit sinnvollen Einschränkungen: er beginnt bei 0, kann nur um 1 erhöht werden und nie gesenkt. Genau wegen dieser Einschränkungen ist er besser als ein blankes int, das jeder Programmteil beliebig verändern könnte.

C# · Abstraktion
class Counter
{
    private int _count;

    public Counter()
    {
        _count = 0;
    }

    public void Increase()   // nur erhöhen, nie senken
    {
        _count++;
    }

    public int GetCount()
    {
        return _count;
    }
}

Counter visitors = new Counter();
visitors.Increase();
visitors.Increase();
visitors.Increase();
Console.WriteLine(visitors.GetCount());  // 3
Kapselung vs. Abstraktion

Kapselung = das Wie verstecken (Daten und Implementierung sind privat). Abstraktion = das Was anbieten (eine einfache, sinnvolle Schnittstelle auf höherer Ebene). Die Kapselung ist die technische Voraussetzung für die Abstraktion.

Vererbung – Beispiel Person

C# · Vererbung
class Person
{
    private string _firstName;
    private string _lastName;

    protected Person(string firstName, string lastName)
    {
        _firstName = firstName;
        _lastName = lastName;
    }

    protected string FullName()
    {
        return $"{_firstName} {_lastName}";
    }
}

class Employee : Person        // Employee IST EINE Person
{
    private string _company;

    public Employee(string firstName, string lastName, string company)
        : base(firstName, lastName)      // Basiskonstruktor aufrufen
    {
        _company = company;
    }

    public string Describe()
    {
        return $"{FullName()} working at {_company}";   // geerbte Methode
    }
}

Polymorphie – Beispiel Rechenoperationen

Der abstrakte Typ Operation tritt in verschiedenen Gestalten auf: Add, Sub, Mul, Div. Value.Calculate muss keine davon kennen.

C# · Polymorphie
abstract class Operation
{
    protected double Operand;

    protected Operation(double operand)
    {
        Operand = operand;
    }

    public abstract double Perform(double x);   // keine Implementierung
}

class Add : Operation
{
    public Add(double operand) : base(operand) { }
    public override double Perform(double x) { return x + Operand; }
}

class Sub : Operation
{
    public Sub(double operand) : base(operand) { }
    public override double Perform(double x) { return x - Operand; }
}

class Mul : Operation
{
    public Mul(double operand) : base(operand) { }
    public override double Perform(double x) { return x * Operand; }
}

class Div : Operation
{
    public Div(double operand) : base(operand) { }
    public override double Perform(double x) { return x / Operand; }
}

class Value
{
    public double State;
    public Value(double value) { State = value; }

    public Value Calculate(List<Operation> operations)
    {
        double tmp = State;
        foreach (Operation operation in operations)
        {
            tmp = operation.Perform(tmp);   // welcher Typ? egal!
        }
        return new Value(tmp);
    }
}

Value x = new Value(7);
Value result = x.Calculate(new List<Operation> {
    new Add(1), new Div(2), new Sub(1), new Mul(2)
});
Console.WriteLine(result.State);   // 6

Rechenweg: 7 + 1 = 8 → 8 / 2 = 4 → 4 − 1 = 3 → 3 · 2 = 6.

Klassen und Objekte

Eine Klasse beschreibt als Bauplan die Gemeinsamkeiten einer Menge von Objekten: alle Attribute, die sie kennzeichnen, und alle Methoden, die ihre Funktionalität beschreiben. Ein Objekt (= Instanz) ist ein konkretes Exemplar, das nach diesem Bauplan im Speicher angelegt wird und eigene Werte für die Attribute besitzt.

KlasseObjekt / Instanz
BildBauplan eines Hausesdas konkrete Haus an der Bahnhofstrasse 3
Existiertim Quellcodezur Laufzeit im RAM
Anzahleinmalbeliebig viele
Wertenur die Deklarationeigene Werte je Objekt
Geometrie-BeispielKlasse Rectangle (alle Rechtecke)das Rechteck 3 cm × 5 cm

Klasse definieren und instanziieren

Mit einer Klasse erzeugst du einen eigenen Datentyp. Elementare Datentypen (int, double, …) speichern nur einen Wert – eine Klasse speichert mehrere Attribute plus Verhalten. Konvention: eine Datei pro Klasse, Dateiname = Klassenname (Rectangle.cs).

C# · Klasse, Konstruktor, Methode
class Rectangle
{
    private int _width;          // Attribute = Instanzvariablen
    private int _length;

    public Rectangle(int width, int length)   // Konstruktor
    {
        _width = width;
        _length = length;
    }

    public int CalculateArea()                // Methode
    {
        return _width * _length;
    }
}

// Verwendung
Rectangle myRectangle;                       // 1. Referenzvariable (nur Verweis)
myRectangle = new Rectangle(4, 6);           // 2. new legt Objekt im RAM an
Console.WriteLine(myRectangle.CalculateArea());   // 24
Was new genau macht

Schritt 1: Rectangle myRectangle; reserviert nur Speicher für die Referenz (einen Zeiger). Das Objekt existiert noch nicht. Schritt 2: new Rectangle(4, 6) legt das Objekt im RAM an, führt den Konstruktor aus und gibt die Referenz darauf zurück. Objekte derselben Klasse unterscheiden sich in ihren Attributwerten und in ihrer Speicheradresse.

Member einer Klasse

Alles, was in einer Klasse steht, heisst Member (Mitglied):

  • Attribute – speichern Daten. Unterteilt in Fields (Felder) und Properties (Eigenschaften), siehe Kapitel 06.
  • Methoden – führen Aktionen aus.
  • Konstruktoren – erzeugen und initialisieren das Objekt.

Attribute werden in der Klasse ausserhalb jeder Methode deklariert. Variablen innerhalb einer Methode sind lokale Variablen und verschwinden mit dem Methodenaufruf.

Sichtbarkeiten

Sichtbarkeiten (Zugriffsmodifizierer) steuern, wer welche Klasse und welches Member verwenden darf. Sie können – und sollen! – auf Klassen und deren Member gesetzt werden. In C# gibt es die vier Schlüsselwörter public, private, protected, internal.

ModifiziererSichtbar fürAuf class?Typischer Einsatz
public überall – eigene Klasse, Nachbarklassen, andere Projekte/Assemblies. Erscheint in IntelliSense. ja öffentliche API: Instanzen erzeugen, Methoden aufrufen
private nur in der gleichen Klasse selbst nein Kapselung: Zugriff von aussen verhindern
protected eigene Klasse + abgeleitete Klassen nein von aussen unsichtbar, aber in Spezialisierungen nutzbar
internal nur innerhalb des eigenen Assembly (desselben kompilierten Projekts, z. B. dieselbe .dll/.exe) ja interne Helfer verstecken, öffentliche API sauber halten
Merkhilfe internal

internal verhält sich innerhalb des Projekts wie public und ausserhalb des Projekts wie private.

C# · Lese- und Schreibzugriff steuern
public class Konto
{
    private string _geheimeNotiz;                // nur in dieser Klasse sichtbar
    protected double Limite;                     // auch in abgeleiteten Klassen
    internal int FilialId;                       // nur im eigenen Projekt

    public double Saldo { get; private set; }    // aussen lesen, intern schreiben
    public string Iban { get; init; }            // nur bei Erstellung setzbar

    public void Einzahlen(double betrag)         // kontrollierter Schreibzugriff
    {
        if (betrag > 0) Saldo += betrag;
    }
}

Spezialfall: privater Konstruktor

Auch ein Konstruktor kann private sein, um die Instanziierung zu steuern – z. B. damit Objekte nur über eine statische Factory-Methode entstehen. Wird beim Testing oft verwendet, um Testdaten immer gleich zu erzeugen.

C# · privater Konstruktor
public class TestPerson
{
    public string Name { get; init; }

    private TestPerson(string name)   // von aussen NICHT aufrufbar
    {
        Name = name;
    }

    public static TestPerson Standard()
    {
        return new TestPerson("Max Muster");
    }
}

TestPerson p = TestPerson.Standard();   // einziger Weg

Methoden und Konstruktoren

Signatur und Rumpf

C# · Aufbau einer Methode
public    double   Distanz   (Kreis ziel)        {  ...  }
//  ↑         ↑         ↑           ↑               ↑
// Sicht-  Rückgabe-   Name      Parameter        Rumpf (Body)
// barkeit   typ
// └──────── Signatur (Name + Parameterliste) ────┘
  • Signatur = Methodenname + Parameterliste (Typ, Anzahl und Reihenfolge der Parameter). Sie ist die „Visitenkarte“: daran erkennt der Compiler, welche Methode gemeint ist.
  • Rumpf = der Code zwischen den geschweiften Klammern, also wie die Methode arbeitet.
  • Der Rückgabetyp allein genügt nicht, um zwei Methoden zu unterscheiden – zwei Methoden dürfen sich nicht nur im Rückgabetyp unterscheiden.

Namenskonvention für Methodennamen: PascalCase / UpperCamelCase. Methoden werden immer innerhalb einer Klasse deklariert – sie „leben“ dort, wo sie thematisch hingehören (Schrank-Funktionen zum Schrank, Dusch-Funktionen zur Dusche).

Rückgabewerte

Der Rückgabetyp steht in der Signatur, direkt vor dem Methodennamen. Eine Methode kann zurückgeben:

RückgabeBedeutungTypischer Zweck
voidgibt „nichts“ zurückZustandsänderung
int, double, bool, string…fundamentaler DatentypBerechnung, Zustandsabfrage
ein Objekt, z. B. KreisReferenz auf ein ObjektAufgabe, Berechnung, Zustandsabfrage
C# · void und return
public void Reset()              // gibt nichts zurück
{
    _count = 0;
    return;                      // optional: beendet die Methode vorzeitig
}

public int GetCount()            // muss einen int zurückgeben
{
    return _count;               // return ist hier Pflicht
}

Parameter

  • Übergeben Informationen an die Methode. Reihenfolge und Typ sind fix; die Anzahl ist beliebig (auch null).
  • Default-Parameter: public void Log(string text, bool laut = false) – der Aufruf Log("hi") genügt.
  • Nullable-Parameter: public void SetBoss(Employee? boss) – darf null sein.
  • Listen und Arrays sind als Parameter möglich: void Print(List<string> namen).
  • Auch Methoden können als Parameter übergeben werden; die Kurzschreibweise dafür sind Lambda Expressions.

Konstruktoren

  • Heisst exakt wie die Klasse und hat keinen Rückgabetyp (auch kein void).
  • Wird beim new automatisch ausgeführt und initialisiert das Objekt.
  • Default-Konstruktor: der parameterlose Konstruktor. Definierst du gar keinen Konstruktor, erzeugt der Compiler ihn automatisch. Sobald du einen eigenen Konstruktor schreibst, ist der automatische weg – dann musst du den parameterlosen selbst ergänzen, falls du ihn brauchst.
  • Überladen: mehrere Konstruktoren mit unterschiedlicher Parameterliste.
C# · Konstruktoren überladen + this/base
class Rectangle
{
    private int _width;
    private int _length;

    public Rectangle()                       // Default-Konstruktor
        : this(1, 1)                         // this(...) ruft anderen Konstruktor
    { }

    public Rectangle(int seite)              // Quadrat
        : this(seite, seite)
    { }

    public Rectangle(int width, int length)  // Hauptkonstruktor
    {
        this._width = width;                 // this = dieses Objekt
        this._length = length;
    }
}

class Square : Rectangle
{
    public Square(int seite)
        : base(seite, seite)                 // base(...) = Konstruktor der Basisklasse
    { }
}
this und base

this = dieses Objekt. Nützlich, wenn Parameter und Attribut gleich heissen (this.name = name;) und für Konstruktor-Verkettung : this(...).
base = die Basisklasse. : base(...) ruft deren Konstruktor auf, base.Methode() ruft deren Implementierung auf – typisch in einem override, wenn du das Basisverhalten erweitern statt ersetzen willst.

Statische Methoden

VorteilEinschränkung
Keine Instanz nötig – die Methode gehört zur Klasse, nicht zu einem Objekt. Kein Zugriff auf Instanzvariablen und Instanzmethoden (kein this).
Ideal für Berechnungen und Hilfsfunktionen ohne Objektzustand. Zugriff nur auf statische Variablen und Methoden der Klasse.
Aufruf direkt über Klassenname.Methodenname(…), z. B. Math.Abs(-25). Nicht über ein Objekt aufrufbar.
C# · static
class MathHelper
{
    private int _letztesResultat;            // Instanzvariable

    public static int Quadrat(int x)
    {
        // _letztesResultat = x * x;         // FEHLER: statisch → kein Instanzzugriff
        return x * x;
    }
}

int y = MathHelper.Quadrat(5);               // richtig: über den Klassennamen
Console.WriteLine(Math.Abs(-25));            // 25 – kein Math-Objekt nötig

Nullable ?

Das Fragezeichen hinter einem Typ markiert ihn als „darf null sein“. Bei Werttypen (int, double, bool) wird der Typ dadurch überhaupt erst null-fähig; bei Referenztypen (string, eigene Klassen) sagst du dem Compiler damit, dass null hier beabsichtigt ist – ohne ? warnt er dich.

C# · nullable
int? alter = null;               // Werttyp, der null sein darf
string? spitzname = null;        // Referenztyp, null ausdrücklich erlaubt
Employee? boss = null;           // z.B. der CEO hat keinen Chef

// Immer prüfen, bevor man darauf zugreift:
if (boss != null)
{
    Console.WriteLine(boss.Describe());
}

Console.WriteLine(boss?.Describe());          // null-conditional: ruft nur auf, wenn nicht null
Console.WriteLine(spitzname ?? "unbekannt");  // null-coalescing: Ersatzwert
int sicheresAlter = alter ?? 0;

UML-Klassendiagramm

UML (Unified Modeling Language) dient der grafischen Modellierung von Klassen, Schnittstellen und deren Beziehungen. Ganze Systeme lassen sich damit darstellen, bevor sie implementiert werden – typischerweise in der Konzeptionsphase eines Projekts. Alle Entwickler können so ihre Absichten in einer allgemein verständlichen Sprache zeigen.

Wann ist UML sinnvoll? (mögliche Prüfungsbeispiele)

  • Konzeptionsphase: Struktur planen, bevor eine Zeile Code geschrieben wird
  • Kommunikation im Team und mit dem Kunden – sprachunabhängig und ohne Code-Details
  • Dokumentation eines bestehenden Systems, Einarbeitung neuer Entwickler
  • Vererbungshierarchien und Beziehungen zwischen Klassen auf einen Blick prüfen

UML → C# übersetzen

C# · aus der Box oben
public class Kreis
{
    private double mittelpunktX;
    private double mittelpunktY;
    public double Radius { get; set; }

    public Kreis(double x, double y, double r)
    {
        mittelpunktX = x;
        mittelpunktY = y;
        Radius = r;
    }

    public double Distanz(Kreis ziel)
    {
        double xDiff = mittelpunktX - ziel.mittelpunktX;
        double yDiff = mittelpunktY - ziel.mittelpunktY;
        return Math.Sqrt(xDiff * xDiff + yDiff * yDiff);
    }

    public double Flaeche()
    {
        return Math.PI * Radius * Radius;
    }
}

Vererbung

Definition: Vererbung bedeutet, dass eine Klasse die Membervariablen und Methoden einer anderen Klasse übernimmt.

  • Basisklasse (in Java auch Superklasse): die Klasse, von der geerbt wird – die Generalisierung.
  • Abgeleitete Klasse: die Klasse, die erbt und erweitert wird – die Spezialisierung.

Die abgeleitete Klasse kann zusätzliche, spezifischere Attribute und Methoden hinzufügen und bestehende Methoden überschreiben. Es gilt: eine abgeleitete Klasse kann mindestens alles, was die Basisklasse kann – und oft mehr.

Beispiel: Shape ist die Generalisierung, die Gesamtheit aller Formen. Rectangle, Circle, Square sind Spezialisierungen – erst sie bringen die Generalisierung in die Realität. Ebenso ist «Car» verallgemeinert; erst die Spezialisierung macht daraus ein konkretes Auto, z. B. einen BMW i3.

Der «ist ein»-Test

Entscheidungsregel

Vererbung passt immer dann, wenn du eine «ist ein»-Beziehung formulieren kannst – und zwar in nur einer Richtung.
✓ Jeder Manager ist ein Mitarbeiter. Aber nicht jeder Mitarbeiter ist ein Manager. → Manager : Mitarbeiter
✗ Ein Motor ist kein Auto – ein Auto hat einen Motor. Bei «hat ein» nimmt man kein Erben, sondern ein Attribut (Komposition).

Einfachvererbung und object

  • In C# und Java kann eine Klasse nur von genau einer anderen Klasse erben (Einfachvererbung).
  • Mehrfachvererbung von mehreren Klassen gleichzeitig ist nicht erlaubt.
  • Ohne angegebene Basisklasse erbt jede Klasse automatisch von object, der gemeinsamen Wurzel aller Klassen.

Vererbung in der Anwendung

C# · Mitarbeiter / Manager
class Mitarbeiter
{
    public string Name { get; set; }
    public int Alter { get; set; }

    public void Arbeiten()
    {
        Console.WriteLine($"{Name} arbeitet.");
    }
}

class Manager : Mitarbeiter        // erbt automatisch alles aus Mitarbeiter
{
    public string Abteilung { get; set; }

    public void Leiten()
    {
        Console.WriteLine($"{Name} leitet die Abteilung {Abteilung}.");

Die erste Stolperfalle: new verdeckt nur

Definiert die abgeleitete Klasse eine Methode mit demselben Namen, verdeckt sie die Basismethode. In C# muss man das explizit mit new kennzeichnen. Das ist kein echtes Überschreiben, sondern nur ein Verstecken – beide Versionen existieren nebeneinander im Speicher.

{
    public void Speak()
    {
        Console.WriteLine("Ein Tier macht ein Geräusch");
    }
}

{
    public new void Speak()                  // verdeckt, überschreibt nicht
    {

    }

a.Speak();      // "Ein Tier macht ein Geräusch"  ← die Referenz entscheidet!

Dog d = new Dog();

Prüfungsfrage-Klassiker

Bei new entscheidet der Typ der Referenz (die Variable links), welche Methode läuft. Bei virtual/override entscheidet der tatsächliche Objekttyp (das new X() rechts). Diese Unterscheidung ist die häufigste „Was gibt der Code aus?“-Aufgabe.

Polymorphie: virtual, override, abstract

Poly = viele, Morph = Form → Vielgestaltigkeit. Ein Objekt kann in verschiedenen Formen auftreten. Alltagsbild: Ein Mitarbeiter ist auch eine Person – je nach Kontext nutze ich ihn als «Person» (Name, Alter) oder als «Mitarbeiter» (Lohn, Abteilung).

Technisch: Eine Referenz vom Typ der Basisklasse kann auf Objekte abgeleiteter Klassen zeigen, und der tatsächliche Objekttyp bestimmt das Verhalten. Vorteil: man kann einheitlich mit vielen unterschiedlichen Objekten umgehen, z. B. in Listen und Schleifen.

C# · polymorphe Referenzen
Animal a1 = new Dog();
Animal a2 = new Cat();

List<Animal> tiere = new List<Animal> { new Dog(), new Cat(), new Bird() };
foreach (Animal tier in tiere)
{
    tier.MakeNoise();     // jedes Tier antwortet auf seine Art
}

virtual und override

  • virtual in der Basisklasse: diese Methode darf in abgeleiteten Klassen überschrieben werden. Eine Implementierung ist vorhanden.
  • override in der abgeleiteten Klasse: ersetzt die geerbte Implementierung. Dadurch wird beim polymorphen Aufruf die richtige Implementierung verwendet.
C# · die Lösung
class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Ein Tier macht ein Geräusch");
    }
}

class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Wuff!");
    }
}

Animal a = new Dog();
a.Speak();      // "Wuff!"  ← jetzt entscheidet das Objekt, nicht die Referenz

Abstrakte Klassen

Animal ist kein konkretes Tier – die Klasse steht nur als allgemeiner Bauplan. Ein Animal kann vieles sein: Hund, Katze, Vogel … aber nicht selbst existieren. Wenn eine Klasse nicht direkt instanziiert werden darf, sondern nur als Grundlage für andere Klassen dient, macht man sie abstract.

  • Eine abstrakte Klasse kann gemeinsame, fertig implementierte Eigenschaften und Methoden enthalten (wie eine normale Klasse) …
  • … und zusätzlich abstrakte Methoden, die von den abgeleiteten Klassen zwingend überschrieben werden müssen.
  • Eine abstrakte Methode hat keine Implementierung (kein Rumpf, nur Semikolon) und darf nur in einer abstrakten Klasse stehen.
  • Eine abstrakte Klasse verbietet virtual nicht – sie ändert nur, dass keine direkten Objekte dieser Klasse erstellt werden dürfen.
C# · abstract
abstract class Animal
{
    public abstract void MakeNoise();      // kein Rumpf → Pflicht zum Überschreiben

    public void DoEat()                    // fertige Methode, gilt für alle
    {
        Console.WriteLine("Das Tier frisst.");
    }
}

class Dog : Animal
{
    public override void MakeNoise()       // MUSS implementiert werden
    {
        Console.WriteLine("Wuff!");
    }
}

class Cat : Animal
{
    public override void MakeNoise()
    {
        Console.WriteLine("Miau!");
    }
}

// Animal a = new Animal();     // FEHLER: abstrakte Klasse ist nicht instanziierbar
Animal hund = new Dog();        // erlaubt: Referenz vom abstrakten Typ
hund.MakeNoise();               // Wuff!
hund.DoEat();                   // Das Tier frisst.  (geerbt, nicht überschrieben)

Cat und Dog implementieren DoEat() also nicht – für sie gilt dieselbe Implementation wie in Animal.

Damit ist erreicht: Animal kann nicht mehr instanziiert werden (es ist nur noch ein Bauplan), und MakeNoise() muss in Animal nicht mehr implementiert werden – keine «???»-Ausgabe mehr, jede Tierklasse weiss selbst, wie sie klingt.

Eine vollständig abstrakte Klasse ist gleich aufgebaut wie ein interface – beide sind nicht instanziierbar. Interfaces kommen später im Modul; dann wird auch klar, warum sie meistens mehr Sinn machen als abstrakte Klassen.

V01Cylinder – Attribute, Methoden, static

Klasse Cylinder mit lesbaren und beschreibbaren Attributen Radius und Height, sechs Berechnungsmethoden und einer überladenen statischen GetSurfaceArea(double, double).

Lösung
Cylinder.cs
public class Cylinder
{
    public double Radius { get; set; }
    public double Height { get; set; }

    public Cylinder()                              // Default-Konstruktor: nötig für new Cylinder()
    {
    }

    public Cylinder(double radius, double height)  // überladen
    {
        Radius = radius;
        Height = height;
    }

    public double GetDiameter()                    // d = 2r
    {
        return 2 * Radius;
    }

    public double GetCircumference()               // U = 2*pi*r
    {
        return 2 * Math.PI * Radius;
    }

    public double GetBaseArea()                    // G = pi*r^2
    {
        return Math.PI * Radius * Radius;
    }

    public double GetLateralArea()                 // M = 2*pi*r*h
    {
        return 2 * Math.PI * Radius * Height;
    }

    public double GetVolume()                      // V = G * h
    {
        return GetBaseArea() * Height;
    }

    public double GetSurfaceArea()                 // O = 2G + M
    {
        return 2 * GetBaseArea() + GetLateralArea();
    }

    // Statische Überladung: kein Objekt nötig, deshalb auch kein Zugriff
    // auf Radius/Height - alle Werte kommen über die Parameter herein.
    public static double GetSurfaceArea(double radius, double height)
    {
        return 2 * Math.PI * radius * radius + 2 * Math.PI * radius * height;
    }
}
Worauf es hier ankommt

1. Sobald du den Konstruktor mit zwei Parametern schreibst, verschwindet der automatische Default-Konstruktor – new Cylinder() kompiliert dann nicht mehr. Deshalb muss der parameterlose Konstruktor explizit dastehen.
2. Die Instanzmethode GetSurfaceArea() und die statische GetSurfaceArea(double, double) haben unterschiedliche Parameterlisten – also unterschiedliche Signaturen – und dürfen gleichzeitig existieren.
3. Die statische Methode kann nicht GetBaseArea() aufrufen, weil das eine Instanzmethode ist. Deshalb steht dort die ganze Formel.

Klassischer Getter/Setter-Weg (wie in Java)
public class Cylinder

    private double _height;

        if (radius > 0) _radius = radius;      // Validierung ist jetzt möglich!
    }

Antwort auf die Zusatzaufgabe: In C# nimmt man dafür Auto-Properties – public double Radius { get; set; }. Sie erledigen Getter und Setter in einer Zeile, der Compiler legt das versteckte Backing Field selbst an, und der Aufruf bleibt lesbar (c1.Radius = 5.25; statt c1.SetRadius(5.25);).

Empfohlene Kurzform (drei Varianten je nach Anforderung)
public class Cylinder
{
    public double Radius { get; set; }          // frei lesen und schreiben
    public double Height { get; set; }
}

// Wenn der Wert nur intern geändert werden darf:
//   public double Height { get; private set; }
// Wenn er nach der Erstellung unveränderlich sein soll:
//   public double Height { get; init; }
Aber Achtung

Eine reine Auto-Property { get; set; } kann nicht validieren. Sobald du eine Prüfung brauchst (Radius > 0), nimmst du die Langform mit Backing Field: set { if (value > 0) _radius = value; }.

V03Cuboid – unveränderliche Attribute und Geometrie

Klasse Cuboid mit Length, Width, Height, die zur Laufzeit nicht geändert werden dürfen. Dazu die drei Zylinder-Methoden: passenden Quader um den Zylinder, passenden Quader in den Zylinder, und eine Prüfung, ob ein gegebener Quader hineinpasst.

Lösung
Cuboid.cs
public class Cuboid
{
    // { get; init; } = nur bei der Erstellung setzbar -> zur Laufzeit unveränderlich
    public double Length { get; init; }
    public double Width { get; init; }
    public double Height { get; init; }

    public Cuboid(double length, double width, double height)
    {
        Length = length;
        Width = width;
        Height = height;
    }

    public double GetBaseArea()        // Bodenfläche
    {
        return Length * Width;
    }

    public double GetVolume()          // V = l * b * h
    {
        return GetBaseArea() * Height;
    }

    public double GetSurfaceArea()     // O = 2*(lb + lh + bh)
    {
        return 2 * (Length * Width + Length * Height + Width * Height);
    }

    public double GetDiagonal()        // Raumdiagonale = Wurzel(l^2 + b^2 + h^2)
    {
        return Math.Sqrt(Length * Length + Width * Width + Height * Height);
    }
}
Ergänzungen in Cylinder.cs
// 1) Kleinster Quader, in den DIESER Zylinder genau hineinpasst:
//    Grundfläche = Quadrat mit Seitenlänge = Durchmesser, Höhe = Zylinderhöhe.
public Cuboid CreateEnclosingCuboid()
{
    double side = GetDiameter();
    return new Cuboid(side, side, Height);
}

// 2) Grösster Quader (quadratische Grundfläche), der IN diesen Zylinder passt:
//    Die Grundflächen-Diagonale darf höchstens dem Durchmesser entsprechen.
//    Bei einem Quadrat gilt: Diagonale = Seite * Wurzel(2)  ->  Seite = d / Wurzel(2)
public double GetFittingCuboidSide()
{
    return GetDiameter() / Math.Sqrt(2);
}

public double GetFittingCuboidHeight()
{
    return Height;
}

// 3) Passt ein gegebener Quader in diesen Zylinder?
//    Bedingung A: Quaderhöhe darf die Zylinderhöhe nicht überschreiten.
//    Bedingung B: die Grundflächen-Diagonale muss in den Durchmesser passen.
public bool Fits(Cuboid cuboid)
{
    double baseDiagonal = Math.Sqrt(
        cuboid.Length * cuboid.Length + cuboid.Width * cuboid.Width);

    return cuboid.Height <= Height && baseDiagonal <= GetDiameter();
}
Program.cs – Ergänzung
Cylinder c1 = new Cylinder(5.25, 20.5);
Cuboid test = new Cuboid(8.0, 8.0, 19.0);

if (c1.Fits(test))
{
    Console.WriteLine("Der Quader passt in den Zylinder.");
}
else
{
    Console.WriteLine("Der Quader passt NICHT. Passender Quader:");
    double side = c1.GetFittingCuboidSide();
    Cuboid passend = new Cuboid(side, side, c1.GetFittingCuboidHeight());
    Console.WriteLine($"length = {passend.Length}");
    Console.WriteLine($"width  = {passend.Width}");
    Console.WriteLine($"height = {passend.Height}");
}
Die Geometrie in einem Satz

Von oben betrachtet ist die Frage immer: passt das Quadrat in den Kreis (Diagonale ≤ Durchmesser) oder der Kreis ins Quadrat (Seite = Durchmesser)? Die Höhe wird getrennt davon einfach 1:1 verglichen.

V07Person / Student / Professor – redundanzfrei

Gegeben ist die Main-Methode und die Soll-Ausgabe. Gesucht: möglichst wenig doppelter Code.

Soll-Ausgabe
Giorgia (Student) sagt: "Ich lerne OOP."
Kimo (Student) sagt: "Ich verstehe OOP."
Meinrad (Professor) sagt: "Ich verstehe OOP."
Lösung

Die Analyse der drei Zeilen: Das Satzmuster ist immer gleich (Name, Rolle in Klammern, Satzteil in Anführungszeichen) → Speak() gehört einmal in die Basisklasse. Variabel sind nur zwei Dinge: die Rolle und der gesprochene Satz. Der Satz ist ausserdem in zwei von drei Fällen identisch → er wird virtual mit dem häufigeren Wert als Standard.

Person.cs
public abstract class Person
{
    protected string Name;          // protected: auch in abgeleiteten Klassen nutzbar

    protected Person(string name)
    {
        Name = name;
    }

    // Rolle: jede Unterklasse MUSS liefern -> abstract
    protected abstract string Role { get; }

    // Satz: Standard gilt für die meisten -> virtual, überschreibbar
    protected virtual string Sentence
    {
        get { return "Ich verstehe OOP."; }
    }

    // Das Muster steht nur EINMAL im ganzen Programm:
    public void Speak()
    {
        Console.WriteLine($"{Name} ({Role}) sagt: \"{Sentence}\"");
    }
}
Student.cs / Professor.cs
public class Student : Person
{
    private bool _understandsOop;

    public Student(string name, bool understandsOop)
        : base(name)
    {
        _understandsOop = understandsOop;
    }

    protected override string Role
    {
        get { return "Student"; }
    }

    protected override string Sentence
    {
        get { return _understandsOop ? "Ich verstehe OOP." : "Ich lerne OOP."; }
    }
}

public class Professor : Person
{
    public Professor(string name)
        : base(name)
    {
    }

    protected override string Role
    {
        get { return "Professor"; }
    }

    // Sentence wird NICHT überschrieben -> erbt "Ich verstehe OOP."
}
Program.cs (unverändert aus der Aufgabe)
// Person p = new Person();          // geht nicht, da abstrakt

Person s02 = new Student("Kimo", true);
Person p01 = new Professor("Meinrad");

List<Person> people = new List<Person> { s01, s02, p01 };

foreach (Person p in people)
{
    p.Speak();          // Polymorphie: jede Person antwortet auf ihre Art
}
Warum das die «richtige» Lösung ist

abstract class Person – eine Person an sich gibt es nicht, nur Studenten und Professoren. Die Aufgabe sagt es im Kommentar selbst.
abstract Role – ohne Rolle wäre die Ausgabe unvollständig, also Pflicht.
virtual Sentence – der Standardsatz gilt für Professor und den verstehenden Studenten; nur der lernende Student weicht ab.
Speak() nur einmal – der Formatstring wird nicht dreimal kopiert. Genau das meint «redundanzfrei».
List<Person> – Basisklassen-Referenzen auf abgeleitete Objekte: das Lehrbuchbeispiel für Polymorphie.

Statt abstract string Role könntest du auch GetType().Name verwenden – dann liefert die Klasse ihren eigenen Namen. Das ist kürzer, in der Prüfung aber schwerer zu begründen; bleib bei der expliziten Variante.
